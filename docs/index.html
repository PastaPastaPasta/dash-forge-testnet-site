User guides

Task-oriented guides for using Dash Forge. For how it is built, see the architecture.

GuideRead it when you want to…
Quick startinstall, get an identity, choose storage, publish with dg init, push, and see it on the web
Mirror a GitHub repositorykeep a copy of a GitHub repository that nobody can take down: set it up from the browser with the /mirror wizard, or by hand with the Mirror Action or forge-import
Mirror a GitLab projectthe same for a project on gitlab.com or your own GitLab, with a GitLab CI template
Moving from GitHub or GitLabmove a project over end to end: storage, identity, import, the Mirror Action, cut-over, collaborators, CI and costs
Bring your own storagekeep pack bytes in your own S3-compatible bucket or IPFS node instead of on Platform, from the CLI or the browser
Rotate storage credentialsafter removing a maintainer you shared a repository's storage with, or if your settings-sync key may have leaked (testnet): roll the S3 key, kubo auth or pinning token, update the profile, and the share follows
Storage on your home NASrun RustFS or Garage in Docker on a NAS or Linux box, give it a public https address, and keep a second copy
Run your own IPFS nodeset up a node with one command (dg ipfs up), connect it to the web app, push to it, and keep a copy of someone else's repository with dg ipfs pin
Run your own backendturn a Linux server, PC or NAS with Docker into storage your repositories push to, with one command (backend.sh)
Pin or fork a repositorykeep a copy of someone else's repository on your own storage: fork it to push your own work, or pin it to help host it (dg repo pin)
Collaboratingadd members, work with issues, pull requests, reviews, merges, releases and webhooks
Organizationsown repositories with an N-of-M multisig identity from multisig.dashhq.org: connect it, make requests and sign them with dg org (testnet)
Boardsplan issues and pull requests on a board: columns, fields, iterations and views, from dg board
Bots and agentsadd a bot, say what it may do, ask an agent to work on an issue or pull request, and give it push access to chosen branches (beta)
Who can read whatkeep issues, comments and reviews of a public repository members-only, and know who can read them, what everyone still sees and what can still leak
Environmentskeep configuration and secrets outside git, encrypted for your maintainers or members, and inject them with dg env run
CI and check runsenrol a CI runner with a key that can only report check runs, report results with dg ci report, and see them on commits and PRs
Self-host a CI runnerrun a repository's .forge/workflows on your own machine with forge-runner (nektos/act in Docker), safely
Identity and keysunderstand your identity and limited keys, back it up, recover it, and keep keys safe
If Forge tells you to revoke keysdisable every signing key of your identity but the one in use at once, from the terminal (dg auth keys disable --all-limited) or the web app (Devices & keys), and sign in again
My first push failedfind the fix for the errors a first push usually hits: no network, no credits, the cost guard, no storage, a moved name, a locked key, shallow clones and LFS
What things costknow what each action costs (measured), what comes back, and how to see it before you pay
Check that Forge isn't lying to youread the Verification card, verify proofs and hashes yourself, and run your own copy of the web app
Verify the app you loadedpin a release's IPFS build of the web app, rebuild its CID from the tag, and compare it with the GitHub release and the Forge release on chain

What "coming soon" means

These guides describe what is on master today. Features that are specified but not built yet are marked Coming soon, and nothing marked that way works yet. The main ones:

  • editing files in the browser, and, for private repositories, merges, branch commits, Update branch and applying suggestions in the browser (the CLI has them);
  • members-only releases in a public repository (a private repository's releases are encrypted and work);
  • in the web app, starting or pushing a members-only branch, publishing a branch for fewer people than all members, and sharing a members-only branch outside the members (dg has them).

Members-only issues, comments and reviews, messages to specific people, making posts public, members-only branches and pull requests, environments, and bots are built, in dg and the web app. What can be members-only, and who reads it, is in Who can read what, the single place to check. The features still marked Beta (narrower branches, branch sharing, bots and agents, bot push access, making a repository public, publication dates) work but have rough edges: Known limitations.

Wallet sign-in works on mainnet with DashPay for Android 11.9.2+ or Dash Wallet for iOS 9.1.4+, and on testnet with DashPay for Android's testnet build: see Identity and keys.

Which network

The guides use testnet, the tools' default, where DASH is free test money and the network can be reset; its web app is testnet-forge.dashhq.org. Forge is also live on mainnet at forge.dashhq.org: pass --network mainnet to dg auth new or dg auth login to make it your default. The latest release, v0.3.1, works on both. v0.3.0 works on mainnet, but much of it fails on testnet since testnet moved to protocol 15 (v0.3.1 notes); v0.2.0 works on testnet only. Networks has the details.

The product specification the planned features come from is docs/design/ux-dx-spec.md and docs/roadmap.md.
