Installing Dash Forge

Current release: v0.2.0 (release notes, changelog), the first published release. v0.2.0 predates Forge's mainnet registration, so its binaries work on testnet only and have no wallet sign-in (dg auth login --wallet). There is no mainnet release yet: on mainnet, build from source. The version policy is in VERSIONING.md.

Every release on GitHub Releases ships prebuilt binaries, so on the networks a release knows you do not need Rust, protoc, or the Platform SDK source. Each archive contains:

FileWhat it is
dgthe command-line interface
git-remote-dashthe git remote helper; git runs it for dash:// URLs, so it must be on PATH
forge-relay, forge-importthe relay daemon and the GitHub importer (optional)
forge-runnerthe self-hosted CI runner (optional; guide)
completions/shell completions for dg (bash, zsh, fish, PowerShell)
LICENSE-MIT, LICENSE-APACHEDash Forge's own licenses: use either one
THIRD-PARTY-LICENSESthe licenses of the open-source Rust crates built into the binaries
licenses/the licenses of OpenSSL (Linux archives) and of musl libc (the musl archive), which are built into those binaries
README.md, INSTALL.mdthe project README and this page

Supported platforms

TargetArchiveNotes
x86_64-unknown-linux-gnu.tar.gzglibc 2.35 or newer (Ubuntu 22.04, Debian 12, RHEL 10)
aarch64-unknown-linux-gnu.tar.gzglibc 2.35 or newer
x86_64-unknown-linux-musl.tar.gzfully static: Alpine, older distributions, containers
x86_64-apple-darwin.tar.gzIntel Macs; not signed by Apple, see below
aarch64-apple-darwin.tar.gzApple silicon; not signed by Apple

Archives are named dash-forge-<version>-<target>.tar.gz. Each contains one directory with the same name.

There is no static build for aarch64 Linux yet. On an aarch64 system with glibc older than 2.35, build from source.

Windows

Use WSL and the Linux build. Each release also carries an x86_64-pc-windows-msvc zip, but it has not been tested, and the install script refuses Windows.

Install script (Linux and macOS)

curl -fsSL https://raw.githubusercontent.com/PastaPastaPasta/dash-forge/master/install.sh | sh

The script works as follows. It is short, and you can read it before you run it.

  1. It detects your OS, CPU, and C library (glibc or musl).
  2. It downloads SHA256SUMS and your platform's archive from the latest release.
  3. It checks the archive's SHA-256. On a mismatch it stops with an error and installs nothing.
  4. If the GitHub CLI is installed and logged in, it also runs gh attestation verify. This checks that the archive was built by this repository's release workflow from the release tag. A failed check stops the install. Without gh, only the checksum is checked. SHA256SUMS comes from the same place as the archive, so this catches a corrupt download, not a tampered release. Beyond that, the install relies on HTTPS to GitHub. The script says so when it skips the attestation check. Set DASH_FORGE_ATTESTATION=require to make the check mandatory.
  5. It checks that the new dg runs on this system. Only then does it copy dg and git-remote-dash into ~/.local/bin, replacing any older copies in one step. It also tells you if that directory is not on your PATH. If the new dg does not run, a working install is left as it was.

On Linux, glibc older than 2.35 gets the static musl build automatically.

The script never runs sudo. You can control it with these environment variables:

VariableDefaultEffect
DASH_FORGE_VERSIONlatesta specific release, e.g. 0.2.0; needed for a pre-release such as 0.2.0-rc.1, which "latest" never picks
DASH_FORGE_INSTALL_DIR~/.local/binwhere the binaries go
DASH_FORGE_BINARIESdg git-remote-dashadd forge-relay / forge-import / forge-runner if you want them
DASH_FORGE_COMPLETIONS01 installs bash, zsh and fish completions under ~/.local/share and ~/.config/fish
DASH_FORGE_ATTESTATIONautorequire fails if gh cannot verify the attestation; skip relies on the checksum alone
DASH_FORGE_TARGETdetectedforce a target, e.g. x86_64-unknown-linux-musl on an old glibc

For a system-wide install, run the script with sudo yourself:

curl -fsSL https://raw.githubusercontent.com/PastaPastaPasta/dash-forge/master/install.sh \
  | sudo DASH_FORGE_INSTALL_DIR=/usr/local/bin sh

Then check the install:

dg --version      # dg 0.2.0 (<commit> <target>), then the Forge contracts built in, per network
dg doctor         # git, git-remote-dash (same version as dg), network, identity

dg --version from v0.2.0 lists mainnet as not deployed: that build cannot use mainnet.

Manual download and verification

  1. Download your platform's archive and SHA256SUMS from the release page.

  2. Verify the checksum:

    sha256sum --check --ignore-missing SHA256SUMS          # Linux
shasum -a 256 --check --ignore-missing SHA256SUMS      # macOS

  3. Optionally, verify build provenance. The archives and SHA256SUMS carry GitHub artifact attestations: Sigstore-signed statements that say which workflow built the file, and from which commit and tag. There is no project key to distribute, rotate, or leak.

    gh attestation verify dash-forge-<version>-<target>.tar.gz \
  --repo PastaPastaPasta/dash-forge \
  --signer-workflow PastaPastaPasta/dash-forge/.github/workflows/release.yml

    The checksum only shows that the download matches SHA256SUMS. The attestation also shows that both files came from this repository's release workflow, and not from whoever controls the download. It does not show that the file is the newest release. Anyone who can edit this repository's releases could serve an older, genuinely attested build. Pin DASH_FORGE_VERSION if that matters to you.

  4. Unpack the archive and put dg and git-remote-dash in a directory on your PATH:

    tar -xzf dash-forge-<version>-<target>.tar.gz
install -m 755 dash-forge-<version>-<target>/dg dash-forge-<version>-<target>/git-remote-dash ~/.local/bin/

cargo binstall

cargo-binstall installs the same release archives into ~/.cargo/bin. The crates are not on crates.io (the name dg there belongs to an unrelated project), so point binstall at this repository:

cargo binstall --git https://github.com/PastaPastaPasta/dash-forge dg git-remote-dash

cargo-binstall does not check SHA256SUMS or the attestation. It relies on HTTPS alone. It takes the version to download from Cargo.toml on master. Between a version-bump merge and the matching tag's release, that version has no archives yet, and binstall falls back to compiling from source. That build needs protoc; see BUILDING.md.

macOS: Gatekeeper

The macOS binaries are not signed or notarized by Apple yet. The effect depends on how you download them:

  • install.sh, curl, or cargo binstall: these do not add the quarantine attribute, so Gatekeeper does not check the binaries and they run normally.

  • A web browser: the archive is quarantined, and the first run fails with "dg" cannot be opened because Apple cannot check it for malicious software. After you have checked the checksum (and, if you like, the attestation) as described above, remove the quarantine flag from the unpacked binaries:

    xattr -d com.apple.quarantine dg git-remote-dash forge-relay forge-import forge-runner

Signing and notarization are planned. Until then, the checksum and attestation are how you confirm where a binary came from.

Shell completions

dg completions bash > ~/.local/share/bash-completion/completions/dg
dg completions zsh  > "${fpath[1]}/_dg"            # or any directory on $fpath
dg completions fish > ~/.config/fish/completions/dg.fish
dg completions powershell | Out-String | Invoke-Expression   # add to $PROFILE to keep it

The same scripts are in each archive's completions/ directory. DASH_FORGE_COMPLETIONS=1 sh install.sh installs the bash, zsh and fish scripts for you.

Upgrading and uninstalling

To upgrade, rerun the install script, or cargo binstall with --force. dg doctor reports a git-remote-dash whose version does not match dg.

To uninstall, delete the binaries: rm ~/.local/bin/dg ~/.local/bin/git-remote-dash. Your configuration and identities in ~/.config/dash-forge are left untouched.

Build from source

This works from any commit and needs no release. It is the way to use mainnet from the terminal until a release after v0.2.0. You need:

  • Rust through rustup (the first cargo command installs the toolchain pinned by rust-toolchain.toml);
  • protoc 25 or newer. Distribution packages are often older (Ubuntu's is 3.21 and fails), so install a release from GitHub as BUILDING.md shows;
  • on Linux, a C compiler, pkg-config and the OpenSSL headers. On Debian or Ubuntu: sudo apt-get install build-essential pkg-config libssl-dev, plus curl unzip git ca-certificates on a minimal system.
git clone https://github.com/PastaPastaPasta/dash-forge && cd dash-forge
cargo install --locked --path crates/dg
cargo install --locked --path crates/git-remote-dash

cargo install puts both binaries in ~/.cargo/bin; make sure it is on your PATH, ahead of any older dg in ~/.local/bin. A source build reports the version in Cargo.toml, so a build from master also says dg 0.2.0; dg --version tells them apart by listing mainnet's contract group. Then sign in on mainnet with dg auth login --network mainnet --wallet, which records mainnet as the default for dg and git.

For maintainers: cutting a release

  1. Set version under [workspace.package] in Cargo.toml to the new version, and merge that change to master. That PR runs the release pipeline as a dry run, because it touches Cargo.toml. Make sure all six targets are green.
  2. Tag the merge commit v<version> and push the tag. release.yml then does the rest: it builds all six targets (the five above and the Windows zip) from scratch (no build cache), runs install.sh against the built archives, writes SHA256SUMS, attests the files, and publishes the release with generated notes: the install and verify commands, the web app's CID, a "Networks" block (the contract groups the binaries embed, read from forge-contracts/deployments/ at the tag, as dg --version prints them) and, if docs/releases/v<version>.md exists, a link to it. The run fails before anything is published in two cases: the tag does not match the Cargo.toml version, or the tagged commit is not on master.
  3. Approve three times. Three jobs use the protected release environment, and each waits for a reviewer: attest + publish (the GitHub Release), then, after it succeeds, push forge-relay image (pushes ghcr.io/<owner>/forge-relay:<version>, and :latest for a non-pre-release, built from the checksummed musl archive) and push forge-gateway image (pushes ghcr.io/<owner>/forge-gateway:<version>, and :latest for a non-pre-release, built from the tagged source, with a build provenance attestation stored next to it; its job summary prints the digest to deploy by, see Deploy a release). Approving only the first publishes the release without the images; the image jobs can be approved later from the same run. After the first push of each image, make the package public (owner, once: GitHub → Packages → forge-relay / forge-gateway → Package settings → Change visibility): ghcr creates new packages private, so docker pull and gh attestation verify oci://… fail for everyone else until then.
  4. Record the web app on Forge (owner, by hand). The release also carries the web app's reproducible IPFS build (forge-web-<version>.car and .cid, built on two runners that must agree). Writing the matching Forge release on Forge's own mirror needs the owner's Platform identity, which CI never holds: reproduce the CID locally and run dg release create with the two files, as Verify the app you loaded shows.

If the run fails on a flake, re-run the failed jobs first. On the tag's run page, "Re-run failed jobs" repeats only what failed (a dropped crates connection, a macOS runner timeout) and keeps the built archives. Do that before anything else.

Emergency release without the web CAR. A fix to dg must not wait on the web app's IPFS build. If the web app (IPFS) job keeps failing and the fix cannot wait, a maintainer can run the release without it: Actions → Release → Run workflow, on the v<version> tag, with dry_run off and skip_ipfs on (gh workflow run release.yml --ref v<version> -f dry_run=false -f skip_ipfs=true). It publishes the binaries, SHA256SUMS and the images as usual, behind the same approvals, but no forge-web-<version>.* files, and the release notes say that this release has no web app build. A dispatch runs the tag's own copy of the workflow, so the tag must have been cut after skip_ipfs was added. A tag push never skips the web build. Do not use this for a flake: re-run it first. Ship the web CAR with the next release, and do not record a Forge release for the web app of a tag that has none.

The dry run also runs on a PR that touches Cargo.toml, Cargo.lock, rust-toolchain.toml, a crate's Cargo.toml or build.rs, install.sh, build-support/, the gateway Dockerfile, release.yml or web-ipfs.yml. A PR that changes only crate source does not trigger it: the six-platform build takes about an hour, so after a merge to master that touches crates/ or any of those files the same dry run builds every target. It builds and packages every target and uploads the archives as workflow artifacts. It never attests anything or creates a release. Once release.yml is on master, you can also start one by hand: gh workflow run release.yml --ref <branch> -f dry_run=true.

One-time repository setup (admin). The workflow only publishes from master commits, but the tag itself and the release environment are protected in the repository settings:

  • Settings → Environments → release: add required reviewers, and a deployment rule that allows only tags matching v*.
  • Settings → Rules → Rulesets: a tag ruleset for v* that restricts creating, updating and deleting those tags to maintainers.
