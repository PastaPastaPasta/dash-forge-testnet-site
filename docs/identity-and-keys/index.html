Identity and keys

On Dash Forge, your account is a Dash Platform identity. No company holds it for you. There is no password reset and no support desk. This page explains what an identity is, which keys it has, how to back it up, and how to keep its keys out of places they don't belong.

What an identity is

An identity is a record on Dash Platform with:

  • an id: a 42–44 character base58 string such as ExampLeidentityExampLeidentityExampLeidentEx. It appears in your repository addresses (dash://<id>/<repo>);
  • a set of public keys. Anything you write on Forge is signed by one of them, and Platform checks the signature;
  • a credit balance that pays Platform fees. 1 DASH = 100,000,000,000 credits.

You create an identity by locking some Dash in an asset lock transaction. The locked amount becomes the identity's credits. Forge does not create or fund identities for you; see Costs.

Create one from the terminal with dg auth new, in the web app (Sign in → Create a new identity), or with the Dash bridge (https://bridge.thepasta.org). All three derive the same keys from the same 12 words, so an identity made in one opens in the others. The quick start walks through dg auth new.

Usernames. Platform has a name service, DPNS. Register a username in the web app (Settings → Choose a username: it checks the name is free, shows the fee, about 0.0007 DASH, and signs once with your identity file or the 12 words, which it does not keep), with dg auth name register <label> (the same file or words, once) or in the bridge. Your browser's own key can't sign it: Platform keeps that key to Dash Forge's contracts. Names of 3–19 characters made only of a–z, 0, 1 and - are contested: they go to a masternode vote (0.1 DASH to enter, two weeks on mainnet), and the web app and dg both refuse them and suggest a name with another digit. The web app resolves usernames: forge.dashhq.org/alice/project, @alice in the header's jump box, and names on profiles and in the wallet sign-in confirmation. So does the CLI: git clone dash://alice/project and dg … alice/project resolve alice (or alice.dash) through DPNS, proof-verified. The identity id still works everywhere.

Look-alike names. DPNS treats only o/0 and i/l/1 as the same letter, so dash-pay, dashpay2 and rnyname (for myname) are names anyone can register. The web app remembers, in your browser only and per network, the owners and repositories you visit, star or follow. When a profile or repository page has a name that looks like one you star or follow but belongs to someone else, it says "Not to be confused with dashpay, which you starred." When it only looks like one you visited, it says both exist, since either could be the real one. Compare the identity id before you trust the page. Clearing the site's data in your browser clears the list.

The keys in an identity

An identity file from the bridge, the web app or dg auth new has five keys, all ECDSA secp256k1, plus the limited keys you add (below):

IdPurposeSecurity levelUsed for
0AUTHENTICATIONMASTERChanging the identity's own keys (add, disable). Nothing on Forge needs it.
1AUTHENTICATIONHIGHSigning documents: pushes, issues, comments, reviews, releases.
2AUTHENTICATIONCRITICALWhat HIGH does. Forge uses it only when the file has no HIGH key.
3TRANSFERCRITICALMoving credits to another identity, or withdrawing them.
4ENCRYPTIONMEDIUMPrivate repositories and members-only content in public ones (see Encryption key), and decrypting webhook secrets addressed to a relay you run.
5+AUTHENTICATIONHIGHLimited keys: what dg, git push and the web app sign with day to day.

What each tool signs with:

  • git push (git-remote-dash) and every dg command that writes, including dg repo create and dg collab add/remove, sign with the key dg auth stored: a limited key. Given a full identity file instead they use its HIGH key, falling back to CRITICAL. Without one they fail with E302.
  • The web app signs with this browser's limited key.
  • The MASTER key signs only one-time steps: registering, topping up or disabling a limited key (dg auth login, dg auth keys add|disable, dg auth logout --disable, and the web app's Import, Renew, Top up and Revoke). It is used for that one signature and not stored.

Backup and recovery

The 12 words are the identity. Every key above is derived from the 12-word mnemonic the bridge showed you when it created the identity. Anyone who has those words controls the identity and its credits. If you lose them, and every copy of the identity file, nobody can recover the identity. Not the Forge project, not Dash Core Group, not anyone.

Do this once:

  1. Write the 12 words on paper, in order. Keep two copies in separate places.
  2. Keep the words offline. Do not put them in a password manager that syncs, in a note-taking app, or in a screenshot.
  3. Treat the identity file (dash-identity-<id>.json) like the words. It contains them, plus every private key. Keep it offline once you have signed in: dg auth login stores only a limited key and the encryption key. If you keep it on disk, keep it chmod 600; dg doctor warns when an identity file it uses is readable by other users, and dg doctor --fix tightens it.

If you lose a laptop but still have the words or a backup of the file, nothing is lost. Your repositories, issues and history are on Platform, not on your laptop:

  1. On the new machine run dg auth login --mnemonic (type the 12 words) or dg auth login <file> with your backup. It registers a new limited key and stores only that, with the encryption key beside it.
  2. Disable the lost machine's key: in the web app, Settings → Devices & keys lists every key and has Disable (your identity file or recovery phrase signs once); in the terminal, dg auth keys list shows it and dg auth keys disable <id> disables it (or pass --replace <id> to the login above to do both in one update). A limited key can only spend its remaining budget, and only on Forge, until then.
  3. In a browser, Sign in → Other ways to sign in → Use my recovery phrase or identity file (under Advanced there on mainnet) registers a fresh limited key for that browser; the words alone are enough. With DashPay, Use my Dash wallet needs neither.
  4. If you use private repositories, the lost machine also held your encryption key, which a disabled signing key does not protect. Replace it: dg auth keys rotate --encryption (below).

Your repository data needs no backup of its own. Refs, issues and PRs are on Platform. Pack bytes are on Platform or in the storage you chose. Any clone also holds a full copy of the history, and dg reseed --from-local can restore a lost pack copy from it.

Where keys live today

ToolWhere the key isHow it finds it
dgA limited key in the OS keychain: macOS Keychain, Secret Service (Linux) or Windows Credential Manager, service dash-forge, account <network>/<identity id>. Without a keychain: ~/.config/dash-forge/identities/<network>-<id>.key, sealed under a passphrase (Argon2id + XChaCha20-Poly1305, 0600)--identity <source> > DASH_FORGE_KEY > the default dg auth recorded in config.toml
git-remote-dashThe sameDASH_FORGE_KEY, else ~/.config/dash-forge/identities/<owner>.identity.json if that file exists, else the default dg auth recorded
forge-importThe same--identity <source> > DASH_FORGE_KEY
Mirror ActionA CI secret: an inline runner key, or a CI-only identity filethe DASH_FORGE_KEY secret (mirror guide)
Web appA limited key (or a key your wallet granted, with the budget and expiry you approved there; keys from the wallet's older code have no limits, see below), encrypted in the browser's IndexedDB (passkey or passphrase), unlocked for the sessionRegistered once from your identity file, recovery phrase, a new identity, or your wallet; see below

A replaced key is kept. When dg stores a new key where it already keeps one for that identity (a sign-in, a renewal, a wallet sign-in), it first copies the old one beside it: the key file to <network>-<id>.key.bak-<UTC time> (0600), the keychain entry to an entry of the same name with .bak-<UTC time> added (-2, -3, … within the same second). The same goes for a key waiting to be confirmed (.key.pending) and the settings-sync key (.key.sync, which is not an identity key). It never writes over an earlier copy, keeps none when the new key is the same, and says where each copy went (previousKeyKeptAt in --json lists the identity keys). If the old key can't be read, the keychain entry is left as it is and the new key goes to a file; a key file that can't be read is not replaced at all. The settings-sync key is read from the keychain before its file, so when the keychain fails to take it, dg puts it in the sealed .key.sync file only when the keychain holds no sync key for that identity, and says so; otherwise it stores nothing and the sync key already there stays in use. An identity key's copy is a key source like any other (--identity <copy>). Delete one with your file manager or keychain once you no longer need it.

dg auth logout keeps a master key. Before it removes an identity key that holds the master key (or recovery words), it copies it the same way (<network>-<id>.key.bak-<UTC time>, or the keychain entry's .bak-<UTC time> entry) and prints where (keptAt in --json). It does the same with a key it could not open to check: a sealed file whose passphrase was not given (or that changed after it was opened), or an entry or file that does not read as a key. A limited key and the settings-sync key are removed without a copy. If the copy can't be made, the key stays and dg auth logout fails.

A key source (--identity, DASH_FORGE_KEY, the recorded default) is any of:

  • a path to an identity file (bridge JSON), or to a file dg auth sealed under a passphrase. The passphrase comes from DASH_FORGE_PASSPHRASE, or from a prompt on the terminal; git-remote-dash asks on /dev/tty. A git push that dg runs (dg init, dg pr merge) doesn't ask again: dg hands the unlocked key to the helper through a pipe only that git inherits, never through the environment;
  • keychain:dash-forge/<network>/<identity id>, an OS keychain entry;
  • dfk1:<network>:<identity id>:<key id>:<wif>, one limited key in one value, for CI secrets. Pass it in the environment, not as --identity (arguments are visible to other users). dg, git-remote-dash, forge-import and the Mirror Action all accept it.

Things to know:

  • On macOS dg reads and writes the keychain through Apple's /usr/bin/security, so dg, git-remote-dash and upgraded copies of either read the entry without an access dialog. Any program running as you can ask security for it without a prompt: the keychain protects entries at rest and from other users. What dg keeps there is limited identity keys (a budget, an expiry, Forge contracts only), with your identity's encryption key beside them (it reads your private repositories; --signing-only leaves it out), and the storage credentials dg storage add is given, so scope those to the one bucket. A full identity (dg auth login --full-key: master key and recovery phrase) never goes there; it is always a passphrase-sealed file. The GitHub CLI stores its token the same way.
  • Over SSH there is no keychain dialog to answer; use a sealed key file there (DASH_FORGE_NO_KEYCHAIN=1 dg auth login …).
  • --insecure-plaintext stores the key unencrypted (0600) where there is no keychain and no way to type a passphrase. Every later use warns.
  • Key files are owner-only (0600, in 0700 folders) on macOS and Linux. On Windows they rely on your user profile's default permissions, so pick an -o export location only you can read.
  • In the web app, the key never leaves that browser, but any script running on the page can use it while it is unlocked (details). Lock or sign out on shared machines.

Never paste a master key into a web page

A web page is whoever served it. If the page, or a script it loads, is compromised, anything you paste into it is gone.

  • Never paste your MASTER key, your 12 words, or your main identity file into a website. That includes forge.dashhq.org. Nothing on Forge needs them.
  • The web app's Import reads your identity file (or recovery phrase) once: its master key signs one update that registers a limited key for this browser, and is not retained. If you would rather not load the master key into a web page at all, use Sign in → Use dg on your computer: the page shows a dg auth keys add --for-browser … command, dg registers the key with your master key on the terminal and prints a line that only that tab can open (below). Use my Dash wallet also keeps the master key out of the page (the wallet registers the key).
  • Forge asks for your recovery phrase only after you start a key action yourself. Every phrase prompt, in the web app and in dg, shows the same warning: "Your recovery phrase controls your identity. Forge asks for it only after you start a key action yourself, never because a message, an email or a pop-up says so. If you didn't start this, stop here." A page that asks for your words without it, or because a message told you to, is not Forge.
  • For CI, give a pipeline its own limited key: dg auth export --new-key --budget 0.5 --expires 365d --format dfk1 --reveal-secrets -o runner.dfk1 makes one, and the file's one line is the DASH_FORGE_KEY secret.
  • Prefer a copy of the web app that you serve yourself if you do not want to trust the one on forge.dashhq.org.

With limited keys (below) the web app keeps nothing but a limited key (or, after a wallet sign-in, the key the wallet granted). The master key is used only in one-time steps: registering, topping up, renewing or revoking a limited key.

Rotating and disabling keys

Platform lets the MASTER key add new keys to an identity and disable old ones. A disabled key can never sign again. Your identity id, balance and data stay the same.

dg auth keys list                        # every key: purpose, level, budget left, expiry, this computer's
dg auth keys add [--budget 0.25 --expires 180d] [--replace <id> | --keep-current]   # a new key for this computer; disables the one it replaces
dg auth keys add --for-browser <request> [--replace <id>] [--with-encryption-key]   # a key for a browser tab, printed sealed to it
dg auth keys disable <id>                # disable one (limited keys; --force for others)
dg auth keys disable --all-limited       # disable every signing key except this computer's and the master, after listing them
dg auth keys rotate --encryption [--keep-old]   # replace the ENCRYPTION key and move your private repos to it
dg auth logout [--disable]               # forget the key here (and disable it on chain)

add, disable, logout --disable and export --new-key need the master key once: pass --master <identity file>, or type the 12 words when asked. dg never disables the MASTER key, and refuses keys that are not Forge limited keys unless you pass --force.

When to rotate:

  • a laptop or CI secret that held a key was lost or leaked: disable that key, and if it also held the encryption key (any dg auth login with private repos, a browser with private repos enabled), replace the encryption key too;
  • a limited key's budget is nearly spent or it is about to expire: dg auth keys add registers a fresh one and disables this computer's current key in the same update (--replace <id> names another key to disable, --keep-current keeps the current one live on chain, though this computer no longer stores it; dg auth login … --replace <old id> does the same at sign-in).

Told to revoke your keys, or unsure which devices still hold one? Disable them all at once: If Forge tells you to revoke keys.

A browser's own key is managed in the web app: Settings → This browser's key can top it up, renew it or revoke it (below).

If the MASTER key or the 12 words leak, rotating does not help: whoever has them can add keys and disable yours. The identity is lost. Move your credits out with the TRANSFER key to a new identity, and start over there with new repositories: push your clones to them. Repository ownership cannot be transferred, and the attacker now controls everything only the owner can do, such as adding and removing members.

Encryption key (private repositories)

A private repository encrypts its content under a repository key, and each member gets that key wrapped (encrypted) to their identity's ENCRYPTION key. Without one, nobody can add you to a private repository and you cannot create one. Identities from dg auth new, the bridge and the web app carry key 4 for this.

The same key reads members-only content in public repositories: issues, comments and reviews only a repository's members can read. Without it you can still be a member of a public repository and do everything public, and you receive the members key once you set one up and a maintainer runs dg repo keys repair. Writing members-only content without one stops with E306: set up your encryption key first.

Using it from the CLI. Reading or writing a private repository needs the ENCRYPTION key's private half. dg auth login (from the identity file or the recovery phrase) and dg auth new store it beside the limited signing key, where the limited key is kept (the keychain, or a passphrase-sealed file), as the web app's Settings → Members-only and private content does: private repositories work with no master key on disk. dg auth status shows it (Private:). --signing-only (or --insecure-plaintext, which would write it in the clear) stores the signing key alone; a key stored by an older dg is one too, and signing in again with --replace <key id> adds it (dg auth status prints the command). dg auth keys add keeps the encryption keys the key it replaces holds. Without it, private-repo commands stop with E306; DASH_FORGE_KEY=<identity file> works for one command.

dg uses the same stored key for members-only content in public repositories. It opens the key only for a repository with members-only content that you are a member of, so other reads never ask for a passphrase. A key protected by a passphrase is asked for on the terminal; with no terminal (or with --json) and no DASH_FORGE_PASSPHRASE, you see the members-only items as locked, with a note saying how to unlock.

An identity without one can add it. This is Set up your encryption key:

dg auth keys add --encryption
  • One identity update, signed by your MASTER key (your identity file, or your recovery phrase typed when asked). The key is derived from the recovery phrase at the identity's key path with the next key id (m/9'/<coin>'/5'/0'/0'/0'/<id>'), so the words alone recover it; nothing is stored by dg.
  • If the identity already has an ENCRYPTION key, it says so and does nothing.
  • dg auth keys list shows the result.

What it can read. This key can read every private repo you're a member of, and every key you've handed out as a maintainer. Keep it as carefully as your signing keys.

Replacing it after a lost device

dg auth keys rotate --encryption [--master <identity file>] [--keep-old]

It runs the rekey of private-repos.md §5.2, in this order, and prints the plan and its cost before anything is signed:

  1. Adds a new ENCRYPTION key, derived from the recovery phrase at the next key id, so the words alone recover it (one identity update, signed by the MASTER key).
  2. Rotates the key of every private repository you maintain: a new key epoch, wrapped to every member, you first, to your new key. Each costs one wrap per member plus one anchor.
  3. Names the private repositories where you are only a writer, triage or reader. You cannot rotate those. A maintainer's next visit (or dg repo keys repair <repo>) wraps the current key to your new one. Until then, new content there is sealed for the old key.
  4. Disables the old key, unless --keep-old is given or a repository failed to rotate. A disabled key still opens what was sealed for it, so nothing you could read is lost. Whoever holds the old key keeps what was sealed before, but nothing sealed from now on.

The key dg stores beside your limited key (dg auth login) gets the new key too. A repository counts as moved only when a fresh read shows your wrap for its current epoch on the new key. If one is not, every old key stays enabled and nothing is lost. Run the command again: each run adds a fresh key and treats every enabled encryption key as old, since a lost device may have held an earlier run's key too. Other computers and browsers need the new key: sign in again with the words, or in the web app add it from Settings → Members-only and private content.

In the web app, Settings → Members-only and private content stores your encryption key in this browser's vault: from your recovery phrase, your identity file or the key itself, checked against your identity first, or Register a new key for an identity that has none. A wallet sign-in (App Connect v2) does not bring it (below); one the wallet's older code stored earlier stays in the vault. (A wallet sign-in does bring a separate key that only syncs your settings; it opens no repository.) The vault keeps every encryption key you give it, and Add another encryption key adds one more.

Limited keys

A limited key is an identity key with four restrictions:

  • AUTHENTICATION purpose, HIGH security level;
  • bound to the dash-forge contract group: it can sign batches on the group's members only. These are forge-core, forge-collab, forge-community and forge-meta and forge-user (which holds settings that follow your identity), plus any later Forge contract the Forge deployer adds to the group. Identity updates, credit transfers and writes to any other contract are refused at consensus;
  • a budget: the most its transitions can ever take from your identity;
  • an expiry.
WhereBudgetExpires
Browser0.05 DASH90 days (30 days to 1 year)
CLI (dg auth new / login / keys add)0.25 DASH180 days
CI runner (dg auth export --new-key, Mirror Action)0.5 DASH365 days

All are editable at creation (--budget, --expires).

What else the key can sign for. Only the group's owner can add members to the group. That owner is the Forge deployer, and nobody else can take the role: the owner and admins are fixed when the group is created. Before binding a key, dg and the web app check on chain, with proofs, that:

  • the group's owner is the deployer recorded in the app, and the group has no admins;
  • the group holds forge-core and forge-collab;
  • every other member belongs to a contract the deployer owns.

If any check fails, they refuse. A member the app does not know yet, such as a newer Forge contract revision, is accepted and listed before you confirm the key: dg adds a note: line to its explanation, and the web app shows it on the key-creation screen. A member contract the app cannot read is accepted too, because only the pinned owner could have added it, and the note says so. With dg only, pass --strict-group (or set DASH_FORGE_STRICT_GROUP=1, for CI) to refuse anything beyond the contracts your dg knows. See trust roots and forge-v2 § Contract group trust.

From the terminal:

dg auth new [--amount 0.05] [--name alice]      # 12 words → deposit QR → identity + a limited key in the keychain
dg auth login                                   # scan a QR code with DashPay; the wallet adds the limited key
dg auth login <file> | --mnemonic               # or import once; registers a limited key and stores it with the encryption key
dg auth status                                  # identity, name, key, its origin, budget left, expiry, balance, where it is stored
dg auth export --new-key --format dfk1 --reveal-secrets -o runner.dfk1   # a key for CI
dg auth name register <label>                   # a DPNS username

dg auth new shows the 12 words once and asks you to type three of them back. It then shows the deposit address as a QR code and as text. Fund it from any Dash wallet (the faucet on devnets), and dg does the rest: the asset lock, its proof (InstantSend where the network offers one, else a chain lock), and one IdentityCreate that registers the standard keys plus this computer's limited key. The limited key is stored in the keychain before the identity exists, so an interruption never leaves a key nobody holds. An interrupted run resumes with dg auth new --resume (type the words again); the deposit address stays the same. The words are shown only in a terminal, and never with --json or in CI. Without a terminal, --backup-file <new file> is required: the words and keys go only to that passphrase-sealed file (0600, DASH_FORGE_PASSPHRASE without a terminal or with --json) and only its path is printed. --skip-backup-check skips the three-word check in a terminal and needs --backup-file; it never prints or writes the words anywhere else.

Signing in from the terminal with DashPay

dg auth login signs in with the DashPay wallet on your phone (App Connect), so neither the recovery phrase nor the master key touches this computer. Giving it an identity file, --identity <file> or --mnemonic signs in from your identity's master key instead (--full-key and --replace need one of those, and stop with a usage error without); --wallet asks for the wallet explicitly:

  1. dg prints a QR code and the same request as a dashpay://connect link (copy it to the phone if the camera can't read the terminal). In DashPay, open More → Tools → Connections → Scan QR, or open the link on the phone.
  2. The wallet shows "Dash Forge" and the key it is asked for: one limited key (bound to the dash-forge contract group) with dg's proposed limits, 0.25 DASH for 180 days, or --budget / --expires (a wallet grants at most 5 DASH and 365 days). You can keep them or pick another limit in the wallet. Approving adds the key to your identity.
  3. dg reads the answer from Platform (no Forge server is involved, so this works over SSH), checks the key on chain, and shows the identity, its username if it has one, and the budget and expiry the wallet granted. Check that it is the identity your wallet showed and confirm. The key is then stored like any limited key: the keychain, else a passphrase-sealed file (--insecure-plaintext as for dg auth login).

The code is valid for 10 minutes; in a terminal dg offers a new one when it expires (not with --yes), otherwise run the command again. Scan only a code dg printed on this computer: anyone who answers it signs in this terminal as their own identity, which is why dg asks you to confirm the identity, and refuses outright when two identities answer. --yes accepts the identity without asking (for scripts; the code still has to be scanned).

Without a terminal (stdin is not a terminal, or --json), a bare dg auth login does not start a wallet sign-in: it stops at once with E802, stores nothing and waits for nothing, so a script that forgot its identity file fails fast instead of waiting 10 minutes for a phone. A script that does want the wallet says so: dg auth login --wallet --yes (the QR code and the link are printed to stderr as text, --json too). CI should use a dfk1: key in DASH_FORGE_KEY and never log in at all.

dg checks before it shows a code that it can store the key (a keychain, a terminal to type the key file's passphrase in, DASH_FORGE_PASSPHRASE, or --insecure-plaintext). Once the wallet has answered, and before anything is written, dg looks at what storing the wallet's key would overwrite for the identity that answered (not just the default identity): the keychain entry when the keychain takes the key, else the key file. If that is the identity's master key (--full-key), or a key dg cannot open (a sealed file without its passphrase, for example), it asks before the wallet's key replaces it (the old key is copied beside it first, as above), and refuses with --yes. A --full-key file that the wallet's key only replaces as the default stays where it is, and dg says so (masterKeyKeptAt in --json); dg auth logout removes dg's own key file after copying it beside it (see below), so keep your identity file elsewhere too. If the keychain refuses the key, dg falls back to the key file only over a limited key, never over a master key or a file it cannot open. A limited key dg registered earlier stays live on Platform; dg names it so you can disable it.

dg auth status shows each key's origin (Origin:: your DashPay wallet, registered with your recovery phrase, an identity file, a dfk1 key, or the OS keychain for a key an earlier dg stored), its budget left and its expiry, and for a wallet key "Renew in your wallet". --json has the same as keyOrigin (wallet, phrase, file, dfk1, keychain). To renew it, run dg auth login again: the code names the identity (dg prints "This code renews …") and reads only that identity's answer, and the wallet disables the previous key it gave this computer in the same update (dg sends the same connection id, kept in app-connect.toml beside config.toml; a damaged file or id is reported, not replaced). To sign in as another identity instead, run dg auth login --wallet --any-identity. Signing in again as the same identity keeps the encryption key the old key had beside it, when dg can open the stored copy (not a sealed file you replace without its passphrase); a wallet sign-in does not bring one of its own, so private repositories otherwise need dg auth login <file> or --mnemonic once. To disable the key, disconnect Dash Forge in the wallet (Connections), or dg auth keys disable <id> with your master key.

Wallets: DashPay for Android 11.9.2 or later, or Dash Wallet for iOS 9.1.4 or later, on mainnet. On testnet, use DashPay's testnet build: the -testnet.apk on the latest dash-wallet release, installed beside the store app.

A browser key from dg

On a computer where dg is signed in, a browser can get its key without the recovery phrase:

  1. In the web app, Sign in → Other ways to sign in → Use dg on your computer (or Settings → This browser's key → Renew key → With dg). Pick how long the key lives (30 days to a year) and whether the browser should also open private repos. The page shows a command with a one-time request in it:

    dg auth keys add --network testnet --for-browser dfkr1:testnet:Ap… --budget 0.05 --expires 365d [--replace 7] [--with-encryption-key]

  2. Run it. dg shows what the key can spend and what the update costs, asks, signs with your master key (the stored identity file, --master <file>, or your words), and prints one line starting with dfkh1:.

  3. Paste that line into the page and choose a passphrase or passkey. The browser checks the key on chain and keeps it in its vault.

When the page knows your identity (a renewal, or a key this browser already holds), the command carries --for-identity <id> and --replace <key>, and dg refuses before signing if it would make the key for another identity. The printed line is sealed to the tab that showed the request: anyone else who sees it cannot open it, and it opens on that network only. --replace <id> (filled in by Renew) disables the browser's old key in the same update; --with-encryption-key hands over the identity's encryption key too, for private repos. This computer keeps signing with its own key. A key that came from dg renews with dg by default, so renewing never asks for the recovery phrase.

Ways to get one in the web app (Sign in). Where a released wallet can sign you in (mainnet and testnet), the sheet shows Use my Dash wallet, badged Recommended, and Sign in with a passkey; everything else is under Other ways to sign in, and on mainnet the routes that take your recovery phrase are under its Advanced. On a devnet, Create a new identity comes first and the wallet is listed last, marked "Not available yet".

What to expect:

  • One approval for all of Forge. The key covers repositories, issues, pull requests, stars and profiles. The wallet shows the app ("Dash Forge"), your identity, the spending limit (Forge proposes 0.05 DASH) and when the connection expires (Forge proposes 90 days). You can change both before approving.
  • Scan only a code shown on forge.dashhq.org. The request names Forge and nothing about the site that shows it, so a lookalike site can show a code that looks the same, and your wallet cannot tell them apart. If you approve one, that site gets a key that signs Forge writes as you, within the limits you approved. Forge never asks you to scan a code it didn't show you on its own site. If you scanned a code you didn't trust, use Settings → Devices & keys → Disable all other keys (your identity file or recovery phrase signs once). If Forge tells you to revoke keys has the steps.
  • No encryption key for repositories. App Connect v2 gives Forge a signing key, and also the key that syncs your settings, which opens no repository. To read private repositories and members-only content, import your encryption key under Settings → Members-only and private content.
  • Renewing. When the key's budget or time runs low, Forge offers Renew in your wallet: the wallet grants a new key and disables the old one in the same update.
  • Disconnecting it in the wallet disables the key on Platform, on every device that holds it, including one a passkey restored it to. Nothing signs with it after that: each write, and each notification-service request, checks the key on chain first. The next unlock on such a device says "This key was disconnected in your wallet, so sign in again" and offers Forget this key and sign in again. With Stay signed in for public repos on, the next page load says it too.
  • Check the identity yourself. The answer does not prove who sent it: anyone who saw the QR code could answer. Forge refuses if two identities answer. When one does, Forge shows which: compare the username and identity id with the wallet's approval screen. Forge warns when the identity has no username, a username less than a day old, or is not the one this browser already knows. A request expires after 10 minutes; keep the QR code private.
  • A freshly restored wallet may not answer until it has synced. If the wallet says its connection records can't be read, let it finish syncing, then open or scan the code again.

The older code (DashConnect) is gone

The sheet used to offer, behind Show the older code, the older key exchange (DashConnect: one key per Forge contract, with no spending limit or expiry, and a guided "Step 2 of 3" for the other contracts). It was removed in November 2026: every released wallet that answered it also answers App Connect v2, and DashPay for Android 11.9.2 already refused it.

If this browser still holds a key from it:

  • It keeps working. Nothing was deleted from your browser: the key unlocks and signs as before, where its bounds allow.
  • Replace it with a limited key. Settings → This browser's key warns that it has no spending limit, and Replace with a limited key asks your wallet for one approval for all of Forge first (or uses your identity file or 12 words, which also disables the old keys in the same update). A write the old key does not cover (it was bound to one Forge contract) opens the same replacement.
  • A wallet replacement leaves the old key live, held here never to sign, so it no longer counts as "no spending limit". Renew with identity file disables it and keeps you signed in with a fresh key; Revoke on Platform disables it together with the new key and signs this browser out. Disconnect in the iOS wallet doesn't disable it either; Settings → Devices & keys → Disable all other keys does.
  • Its encryption key stays in this browser's vault; replace it if you scanned a code you didn't trust (above).

wallet-login.md has the protocol details, and wallet-primary.md the plan to make the wallet the primary sign-in.

Drafts of the wallet-side fixes (group-scoped, limited grants; a signature that proves which identity answered) are in docs/upstream/, for the owner to file with dashpay.

CI gets one pasteable value, DASH_FORGE_KEY=dfk1:<network>:<identity id>:<key id>:<wif>, in place of a file. dg auth export --format dfk1 writes only limited keys.

Devices & keys

Settings → Devices & keys lists every key on your identity as the network has it: what each is for (master, a Forge key with a budget and an expiry, a key for one Forge contract, encryption, transfer), what is left of its budget, when it expires, and which one this browser signs with. Name a key ("work laptop") to tell them apart; names stay in this browser. Disable turns off a lost device's key for good; your identity file or recovery phrase signs once (about 0.00002 DASH). Disable all other keys does it for every signing key except this browser's and the master, wallet sign-ins and other apps' keys included, 10 keys per update (If Forge tells you to revoke keys). The master key cannot be disabled, this browser's own key goes through Revoke on Platform, and the encryption key is not disabled here, because your private repos open with it: Lost a device? on the same page gives the dg auth keys rotate --encryption command that replaces it (below). Platform does not record when a key was last used: a budget that went down was used, and the page shows when this browser last wrote.

New-key alert. Each browser remembers which keys your identity had when it last looked. When you sign in or unlock and a key has appeared that this browser did not add, a red bar names it. Added it yourself (with dg, another browser, a CI runner)? Choose It was me. If not, choose Review keys and disable it: whoever holds your recovery phrase or master key can add keys, so a key you did not add is the first sign of a leak. A new master key means someone else may control the identity (below). The check reuses the identity read every sign-in makes; it costs nothing.

Storage. The vault lives in the browser's storage, which a browser may clear under storage pressure, and Safari clears after 7 days without a visit. Forge asks the browser to keep it when it stores a key (navigator.storage.persist()), and Devices & keys says whether it agreed. If the vault is cleared, sign in again with dg, your identity file or your recovery phrase.

Passkeys for other devices

A passkey added in the web app lets another device sign in without your identity file. Settings → Devices & keys → Passkeys for other devices → Add a passkey makes the passkey, confirms it with a second prompt, and stores a copy of this browser's keys, encrypted to that passkey, on Platform. On the other device, Sign in with a passkey opens them and keeps the session in that browser under the same passkey. It works at https://forge.dashhq.org (mainnet) and https://testnet-forge.dashhq.org (testnet) only (and localhost for development), and only once the network's forge-meta has the passkey vault; a passkey made on one of them doesn't work on the other.

  • It moves a session. It doesn't recover an account. The keys it carries are the limited keys you already have, with their budget and expiry. When the key expires or is disabled, the passkey stops working: renew with your identity file or recovery phrase (or in the wallet that granted it).
  • Every device shares the same key and budget. Disabling the key signs all of them out. The list says which passkey is this device's and which key each holds; Needs update appears when a passkey holds an older key after a renewal, and asks that passkey once to save the new one.
  • Keys without a spending limit stay on this device only. A passkey holds a key only if it has a budget and an expiry, because the encrypted copy is public on Platform for good. A v1 wallet's unlimited per-contract key is left out; the page counts how many.
  • Your encryption key is not included unless you tick it. Once written, it can't be taken back: removing the passkey later does not lock out anyone who has it. Replace the encryption key too (above).
  • Removing a passkey deletes its entry (the deposit comes back); the key it held keeps working. Revoking or disabling a key offers to remove the passkeys that hold it first.

Adding the first passkey costs about 0.0005 DASH from the key's budget (costs). The threat model is in passkey vault.

The browser vault and its limits

The limited key is stored in IndexedDB, encrypted with AES-256-GCM. The data key is wrapped by a passkey's PRF output (stretched with HKDF), by Argon2id of your passphrase (64 MiB, 3 passes, 16-byte salt), or by both. Each ciphertext is bound to its network and identity.

Once unlocked, a session lasts across reloads, typed URLs and new tabs for public repos: up to 12 hours after the unlock, and not after 4 hours without use. It ends at once when you lock or sign out in any tab (every tab locks), or when the key turns out to be disabled or expired on chain. A resumed session holds only a signing key bound to Forge's contracts, with a budget and an on-chain expiry (a browser key: 0.05 DASH and 90 days by default; a wallet's key only when the wallet gave it a budget and an expiry). Anyone with JavaScript running on this site, or a copy of your browser profile taken within the window, could use that key. Your encryption key, storage credentials and wallet grants are never stored unlocked: a reloaded tab asks you to unlock (one passkey gesture, or your passphrase) the first time it needs them, and keeps them in that tab's memory only. The vault holds every encryption key this browser was given (from an identity file, a recovery phrase, a pasted key, a new registration, or each wallet approval), and that one unlock opens all of them, for every repository in the tab. Turn this off with Stay signed in for public repos.

What the vault does not protect against:

  • Script running in the page. The vault protects the key at rest. While it is unlocked, any script running on the page (an XSS) can use it. During the stay-signed-in window a script on any page load of this site can also read the kept signing key and send it off, bounded by that key's budget and on-chain expiry (not the encryption key, storage credentials or wallet grants, which are never kept). The page's CSP allows inline scripts, which Next's static bootstrap needs. It does not allow JavaScript eval, only wasm-unsafe-eval for the SDK's WebAssembly. forge.dashhq.org also runs one third-party script, Cloudflare's Web Analytics beacon, with the page's privileges. The CSP allows only its exact URL and the page pins its bytes by SRI hash, so a changed script is refused, not run (Hosting §6). A build you host yourself has no such script unless you set NEXT_PUBLIC_CF_BEACON_TOKEN.
  • Someone with a copy of your browser profile, taken within the window. The kept record is deleted when the app next runs after it expires, not the moment it does, and the browser may keep the key that seals it in the profile. So a copy taken before your next visit can use the signing key without your passphrase or passkey, until its budget or on-chain expiry runs out, or you revoke it. Nothing else of the vault is in that record. Stay signed in for public repos off closes this.
  • Clickjacking where the host sends no header. frame-ancestors only works as an HTTP header, and GitHub Pages can't send one. A Cloudflare proxy in front of Pages could add it (Hosting the web app lists the headers); none is in front today, so forge.dashhq.org can be framed. A framed page never picks up a kept session, so it opens locked. A copy you host yourself needs Content-Security-Policy: frame-ancestors 'none' too.
  • A shared origin. On a GitHub Pages project site (*.github.io/<repo>) or an IPFS path gateway (ipfs.io/ipfs/…), other sites share the origin and could read the vault or ask the browser for the passkey's PRF output. So the app refuses to create or unlock a vault there. Browsing still works. Use https://forge.dashhq.org (the Pages deployment's custom domain, set in the repository's Pages settings) or an IPFS subdomain gateway (<cid>.ipfs.<gateway>).

Settings that follow your identity

A wallet sign-in can carry your settings to every device where you sign in with a wallet restored from the same recovery phrase. On a device that has never had a wallet sign-in, settings stay on the device that made them, as before.

On mainnet the web app syncs since its deploy of #750. dg syncs on mainnet from the first release after v0.3.1: v0.3.1 and earlier don't know mainnet's forge-user and keep mainnet settings on each computer. On testnet, dg syncs from v0.3.0 (use v0.3.1; v0.3.0 fails on testnet's protocol 15).

How it turns on. When Forge's forge-user contract is on the network (testnet and mainnet), Use my Dash wallet and dg auth login --wallet ask the wallet for one more key: an encryption key bound to forge-user. Every wallet restored from your recovery phrase derives the same one. Forge encrypts your settings under it and stores them as documents of your identity on Platform, which only your identity can write. A passkey, an identity file or a pasted key doesn't bring that key. Your recovery phrase can: Settings → Storage → Add the sync key, or dg storage sync add-key. After a move to a new key that is the only way, because wallet sign-ins no longer carry it. Each sync is a Platform write paid from your key's budget. If your wallet rejects the code or doesn't answer it, the web app asks once more without the extra key and signs you in without sync; with dg, run dg auth login --wallet --no-sync.

What follows you.

  • Storage: your storage profiles with their credentials and your default storage, in the web app and in dg, and the per-repository storage you set in the web app or with dg storage share. On a repository you own, that per-repository storage is also what its maintainers get (Storage for maintainers); your default storage is never shared. dg merges them with storage.toml, where storage.toml's profile wins over a synced one of the same name, and never rewrites that file; dg storage list says where each profile comes from (local, synced, local+synced, …).
  • Display preferences, in the web app only: diff layout, whitespace and colour palette, the merge commit name and email, fiat display, whether your stars count toward Trending, image hosts you allowed, IPFS gateways and the organizations you connected in this browser. Whether this browser reads packs from IPFS peers stays per device.

Nothing local is deleted: the first sync uploads what this device has and keeps the local copy, and the web app uses the synced copy only once it reads back as written.

Where to see it. Settings → Storage has a collapsed line: Synced with your identity, or On this device only with how to turn it on. In the web app the key is held like your private-repository encryption key: in the vault, opened when you unlock, never in the stay-signed-in record. In the terminal, dg doctor has a settings sync row, and dg auth login --wallet says whether sync is on.

What it means for a leaked key. Whoever gets this key can read every setting synced with your identity, storage credentials included, though it signs nothing and opens no repository. A site that tricked you into approving a wallet code gets it too. If that may have happened, move sync to a new key, then rotate your storage credentials: disabling keys does not take this one back. dg auth logout removes it from the computer.

Trust roots

  • The contract group id comes from forge-contracts/deployments/<network>.json, which is built into the app and dg. So is the group's owner, which the same file pins. The owner (and any admins, of which Forge's group has none) is the only identity that can add contracts to the group. Every group-bound key can then sign for those contracts too, including keys registered earlier. Binding a key to the group therefore means trusting its owner, the deployer that registered Forge's contracts on that network: CL4UTHLAyjYDvWNSgzmY7cXiBBba6fDt4BarAqt2XT3y on mainnet and 3pjHaytsQJg5aKZj3VeqwBPccN7uN3bCJiUNkT8KUBwM on testnet. Before binding a key, the app and dg check on chain, with proofs, that the group's owner is the pinned one and that it has no admins. They also cross-check that every member belongs to a contract that owner owns. Members they do not know are listed, not refused. --strict-group (on dg auth new, dg auth login, dg auth keys add and dg auth export --new-key, or DASH_FORGE_STRICT_GROUP=1) refuses them (forge-v2 § Contract group trust). The owner cannot change, so this pin holds for the life of the group.
  • Watching the deposit goes through DAPI, the Dash network's own evonodes: a bloom-filtered subscribeToTransactionsWithProofs feed of the deposit address from the block the creation started at, broadcastTransaction for the asset lock and getTransaction for its height. The web app asks nothing else: it watches on two nodes at once and moves a feed that fails or goes silent to another node. dg falls back to a block explorer (Insight, dg auth new --explorer <url>) when DAPI cannot answer or the feed is idle. No source is trusted with amounts: each deposit output is read from a raw transaction whose txid is computed locally (an explorer's is fetched and hashed against the txid it named) before the asset lock is signed. A lying node or explorer can delay you or hide funds, but it cannot redirect or burn them. If a broadcast is dropped, the signed bytes are kept and sent again.
  • The InstantSend proof comes from the same evonodes. Before the asset lock is broadcast, the web app and dg open subscribeToTransactionsWithProofs feeds on three nodes, filtered on the lock's txid and the outpoints it spends. An InstantSend lock is sent once, live, and never replayed, so the feeds have to be open first. The first lock that names the lock's txid makes the proof. Platform checks its signature itself, so a node cannot fake one. With no lock within a minute, the proof is a chain lock instead, a few minutes slower. So is it for a lock already mined, and for a resumed creation whose lock was already InstantSend-locked, since that lock is not sent again. dg can also poll a getislocks JSON-RPC of your choice alongside the feeds (dg auth new --islock-rpc <url> or islock_rpc in config.toml). None is set by default: the public testnet one, trpc.digitalcash.dev, no longer follows the chain. If Platform refuses an InstantSend proof, dg retries with a chain lock, on a resumed creation too.
  • The quorum keys every proof is checked against come from quorums.<network>.networks.dash.org, as for every read. The web app compares them with a second source on each repository page (Verify Forge).
  • The code doing the checking: the web app you loaded, or the dg you built. If you do not trust forge.dashhq.org, serve the app yourself.

Your public profile

Your profile is the page at /u/?id=<your identity id> (or /u/?name=<username>): your username and id, your follower counts and your repositories. You can add a display name, a bio, a company, a location, up to four links (https only) and an avatar to it. They are one profile document of your identity, which only you can write, change or delete.

It is public. Anyone can read your profile, on any page that shows it, and it is never encrypted: a member of one of your private repositories sees the same profile as everybody else. Put in it only what you would post publicly.

Edit it in the web app (Settings → Public profile, or Edit profile on your own profile page) or with dg:

dg profile set --name "Alice Example" --bio "Builds wallets." --company "Example Co" \
  --location Lisbon --link https://alice.example --link https://mastodon.social/@alice \
  --avatar identicon
dg profile show            # yours; `dg profile show @bob` or an identity id for someone else's
dg profile set --company ""    # an empty value clears a field; a field you don't name is kept
dg profile set --clear-links   # removes every link; --link replaces them all
dg profile delete              # removes the document (part of its deposit comes back)

Both check the same rules before anything is signed: a name, company or location of at most 60 characters on one line, a bio of at most 500 characters (line breaks are fine), and links that start with https:// and hold no spaces. Writing a profile costs about 0.0004 DASH the first time and a fraction of that to edit (see Costs).

Avatars. Forge hosts no images. Your profile page shows one of:

  • Your pattern (the default, or --avatar identicon): a 5×5 pattern every browser draws from your identity id, so nothing is fetched;
  • Another pattern (--avatar identicon:<seed>): the pattern of a seed you choose (a seed that is another identity's id draws your own pattern, so no one can borrow someone else's);
  • Image link (--avatar https://…): a picture you host. Visitors see your pattern until they choose to load images from its host, as with images in issues and comments, because loading it tells that host their IP address.

Everywhere else (beside your comments, repositories and reviews) Forge draws the pattern of your identity id with its first 7 and last 5 characters, whatever your profile says. Anyone can copy a picture or register a similar name, but not that pattern: it changes with every character of the id.

Bot accounts

An identity that runs automation (a CI bot, an importer) can carry a bot badge beside its name in issue and pull request threads, with its operator on its profile page. The badge needs both sides to agree, so no one can label someone else a bot, and no bot can claim an operator who does not vouch for it:

dg profile bot operator @alice     # as the bot: name the identity that runs you ("" clears it)
dg profile bot add @alice-bot      # as the operator: list a bot you run (up to 8)
dg profile bot remove @alice-bot
dg profile show @alice-bot         # "bot  operated by …" once both are set

Each command writes only your own profile, so the badge appears once both identities have run theirs.

Signed commits and Verified badges

If you sign your commits with git (an SSH key with gpg.format=ssh, or an OpenPGP key), publish the key on your profile. Your signed commits then show Verified in the web app, on the commits list, the commit page and a pull request's commits, in every repository you own or are a member of:

dg profile key add                    # the key git signs with (user.signingkey, gpg.format)
dg profile key add --ssh ~/.ssh/id_ed25519.pub
dg profile key add --gpg 0x1234ABCD5678EF90
dg profile key list
dg profile key remove <end of fingerprint>

In the web app, paste the public key (an ssh-ed25519 … line, or the output of gpg --armor --export <key id>) under Settings → Public profile → Signing keys.

  • Which keys. Ed25519 SSH keys, and Ed25519 or ECDSA (P-256/384/521) OpenPGP keys. A profile lists at most four, of at most 300 bytes each, so an RSA key does not fit: add an Ed25519 signing subkey (gpg --quick-add-key <fingerprint> ed25519 sign). For an OpenPGP key, the key that signs is published: the newest subkey that may sign, else the primary key, as gpg picks it.
  • What Verified means. The signature checks against a key that exactly one of the repository's owner and members lists on their profile. The badge names that identity. As with a key on a GitHub account, nobody proves they hold the private key of a key they list. Forge does not tie it to the commit's author email either, which it doesn't know. A key that two identities list names nobody.
  • Signed (neutral, SSH) and Unknown key (neutral, OpenPGP) mean the key is on no member's profile, as with history signed on another host. An SSH signature carries its key, so Forge checks it anyway; an OpenPGP one can't be checked without the key. Signed by GitHub means the signature checks against GitHub's web-flow key, which signs merges and edits made on github.com: the commit was made on GitHub, but the badge names no member. GitHub's 2017 key, retired in 2024, is not trusted. In the web only; dg verify-commit reports these as Unverified, key on no member's profile.
  • Unverified says why: more than one identity lists the key, the signature does not match the commit (it was changed after signing), or it is a kind Forge does not check (X.509, RSA, an SSH key that is not Ed25519, SHA-1).
  • Checked where. In your browser (and by dg): nothing is asked of a server. The web reads the repository's members and their profiles once a page shows a signed commit.

Check commits from a clone with dg verify-commit, which gives the same verdict as the badges:

dg verify-commit HEAD main~3
dg verify-commit --author @bob HEAD    # also trust a pull request author's keys
